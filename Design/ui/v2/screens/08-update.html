Screen 08 · Update

版本更新

更新只有两个问题：「会不会自己更新」（设置里的一个开关）和 「现在要不要装」（一个弹窗）。弹窗只在自动检查关掉时才会出现—— 开着的时候用户什么都不用做，这正是「后台更新」这个词的含义。 因此这一页里，弹窗和设置行是同一个状态机的两个出口，不是两件独立的事。

A · 有新版本 New version

应用不上架 App Store，只走 Developer ID 直发 —— 所以「能不能替换自身」这件事 没有分叉：能，直接画。弹窗只有这一版：主按钮「后台更新并重启」、次按钮「跳过此版本」， 操作区左边再留一个不占按钮的出口（Esc = 稍后）。

「跳过此版本」和「后台更新并重启」之外，第三个出口是 Esc。 只有这两个按钮时，用户被逼着在「永久跳过这个版本」和「现在就重启」之间二选一 —— 而多数人真正想说的是「现在不方便」。Esc / 关窗 = 稍后再提醒， 这个出口不占按钮，但必须写在操作区左边，否则用户不知道它存在。

B · 设置里的「更新」组 States

弹窗关掉之后，状态必须有落点，否则用户无法判断「刚才那下到底生效没有」。 所有中间状态都就地画在设置这一行上：不弹遮罩、不加横幅、 不往主窗口塞东西 —— 后台更新的全部意义就是别打扰用户。

「稍后」也必须有落点。用户按了 Esc，弹窗消失、什么都没留下的话， 他既不知道有新版本、也没有再打开的入口 —— 只能等下次启动。 这一行把「有新版本」这件事留住，并把按钮从「检查更新」换成「查看更新」（主按钮）， 让用户随时能回到那个弹窗。

3 · 后台下载中 · 行内进度，不打断
更新
正在后台下载 1.1.0
42%

百分比是真的，ETA 是编的 —— 所以只画百分比。下载有确定的字节数，进度条说的是实话； 而「还需 1 分钟」在任何网络下都是猜的。（主窗口那条「推出中」不画进度， 理由正好相反：系统的推出接口不提供进度。） 进度条外层固定 16pt，与说明行同高，下载中这一行不会被撑高。

3b · 后台下载中 · 自动更新那条路（无百分比）
更新
正在后台下载 1.1.0
下载完会自动装上，不用你再管。

与 3 说的是同一句话，但没有进度条、也没有「取消」。 「自动检查更新」开着时 Sparkle 走的是另一条路，那一条路不提供任何进度回调， 所以百分比无从得知 —— 画一条停在 0% 的进度条， 用户会盯着它判断「是不是卡住了」（这正是 3 那条「百分比是真的，ETA 是编的」的另一面： 不知道就别猜）。同理，那条路也不给取消入口，于是这一态右侧不放任何按钮 —— 放一个点了没反应的「取消」，与「功能坏了」长得一模一样。 下载完成并校验签名后，这一行直接变成 4（已就绪）。 ⚠️ 这一态反而多了一行说明（3 那一态是进度条占着这一行）： 面板是固定高度，其余各态都有第二行（进度条 / 说明 / 上次检查）， 这一态若只有一句话，实测比别态矮 14.8pt ⇒ 切到它时底部会多出一条空白带。 这行说明必须对「百分比未知」的两种来源都成立（自动那条路的终点是「退出时安装」、 手动那条路刚起步那一瞬的终点是「自动重启」），所以只能写它们共同的那句 「下载完成后会自动安装」—— 写成「退出时安装」对后者就是假的。

4 · 已就绪 · 待重启安装
更新
1.1.0 已下载完成
重启后完成安装；下次退出应用时也会装上。

这一帧是「自动检查开着」那条路：重启不自动做，只提供入口。下载可以完全后台， 但重启会关掉用户手上的一切 —— 那条路的语义是「后台下载，退出时安装」： 下次退出时静默装上，用户想立刻用新版本再点「立即重启」。 点过「后台更新并重启」那条路不一样 —— 见下一帧 4b。

4b · 已就绪 · 点过「后台更新并重启」
更新
1.1.0 已下载完成
会自动重启完成安装；有磁盘正在推出时会等它结束。

点过「后台更新并重启」⇒ 应用会自己重启完成安装。弹窗的提示块 （「完成后自动重启完成安装」）与下载中那一行（「下载完成后会自动安装， 无需你再操作」）都这么承诺过 —— 这一帧就是兑现那句话的样子。
唯一会推迟的情况是「有磁盘正在推出」：那一刻回答安装会立刻退出应用、 把用户的推出打断（而提示块也承诺了「正在推出的磁盘不会被打断」）， 所以推迟到推出结束再重启。是推迟，不是取消 —— 用户什么都不点它也会重启； 不想等就点「立即重启」。

跳过是一个状态，不是一个动作，所以必须画出来。不写这一行， 「点了跳过 → 下次启动没弹窗」与「检查更新坏了」在界面上长得一模一样 —— 与登录项的「等待系统批准」是同一类错误。 而且它必须可撤销：手动点「检查更新」会清掉跳过标记并重新弹窗， 否则用户只能去改偏好文件才能反悔。

6 · 下载失败 · 不用琥珀也不用红
更新
1.1.0 下载失败
网络不可用。下次启动会自动重试。

这一行不染色。琥珀只用于「受阻，且需用户介入才能恢复」（判据见 06-states 的 D 节）； 下载失败会自愈（文案原文「网络不可用。下次启动会自动重试。」）⇒ 不满足第二条判据。 红只表示「破坏性动作」，也不是。借一个已经承担了别的含义的颜色，比没有颜色更糟 —— 用户会以为磁盘出了问题。失败靠文字 + 一个「重试」按钮表达。

设计说明 Rationale

文案原则

  • 标题写版本号，不写「发现新版本」。用户要判断的是「值不值得为它重启一次」， 所以版本号、当前版本、体积、日期四样都要在首屏给全 —— 与推出弹窗「标题带磁盘名」同一条规则。
  • 按钮用动词，且两个按钮都要能单独读懂。「后台更新并重启」而不是「确定」； 「跳过此版本」而不是「忽略」——「忽略」读不出是忽略这一次还是永远。
  • 说清代价与不代价。「正在推出的磁盘不会被打断」这句是必需的： 用户按下更新前最怕的就是「会不会把我正在拷的东西弄坏」。
  • 「跳过」要说清跳过的范围。「跳过此版本」= 只跳这一个版本，下个版本照常提醒。 设置行里也照写「已跳过 1.1.0」，带上版本号，避免被读成「关掉了更新」。

规格 Handoff

  • 弹窗沿用 .alert：宽 400、圆角 14、材质 blur(34) saturate(180)
  • 图标容器 38 × 38，用 --accent-soft（信息态，不是警告态）
  • 更新日志：12 / 400，行高 1.55，项目间距 6，项目符号 ·
  • 提示块沿用 .callout--info：圆角 6、内边距 9 / 11
  • 操作区：提示文案 11 / --text-3 靠左，按钮靠右、间距 8
  • 设置行内进度条：外层固定 16 高，轨道 5、圆角 999，与磁盘行共用 .meter
  • 更新组在设置面板中排第 4 组（诊断之后、关于之前），面板 480 × 920

这一页对实现提出的要求（不是设计稿能自己满足的）

  • 「后台更新并重启」需要一个真正的更新器。当前 UpdateService 只做 「打开下载页」，没有任何下载与安装代码。要落地本页 B 段的第 3–4 帧（后台下载中 / 已就绪）， 必须先有：下载 + 签名校验 + 替换 bundle + 重启。 两条路：引入 Sparkle（多一个 SPM 依赖、EdDSA 密钥、appcast 托管）， 或自写下载 + 校验。在更新器落地之前，弹窗的主按钮只能退回「打开下载页」 （UpdateService.openUpdateSource() 现在做的就是打开 GitHub Releases）—— 先画上「后台更新并重启」再补实现，用户会点到一个什么都不做的按钮。
  • 「已跳过 1.1.0」需要一个新的持久化键（版本号字符串，不是布尔）。 布尔量表达不了「跳过了哪一个」，而按版本号存才能在 1.2.0 时自动恢复提醒。
  • 「有新版本」是第三种状态，不能用布尔量建模。 「检查完了但没有新版本」与「还没检查过」在界面上都是「没有新版本」， 但它们该显示的文字不同（已是最新版本 vs 尚未检查）—— 必须另有一个「检查是否完成 / 上次检查时间」的位。
  • 「不上架」这个决定把一批渠道分支变成了死代码 —— 已于 2026-09-18 删除。 UpdateService.channel 的 .appStore 分支 （App Store 收据判定、appStoreID、macappstore:// 链接、 「在 App Store 中查看」文案）连同两条本地化键一并移除，渠道只剩 .direct / .development 两种。 「不存在」这件事本身钉了两个测试： UpdateServiceTests/不存在AppStore渠道 从枚举反查 appStore， LocalizationCatalogTests/已删除的AppStore渠道文案不再存在 反查两条文案键 —— 谁加回来谁红。删掉而不是「留作防御」的理由：防御的前提是那条路可能存在， 而 MAS 渠道已经不存在了。
  • 「自动检查更新」开着时，中间那一段「后台下载中」画得出来，但不带百分比（2026-09-19 订正）。 Sparkle 在自动下载那条路上选的是 SPUAutomaticUpdateDriver，而它 一个 user driver 回调都不发：showUpdateFound / showDownloadInitiated / showDownloadDidReceiveData / showReadyToInstallAndRelaunch 这四个回调在全库里只有 SPUUIBasedUpdateDriver 一个调用方，而自动那条路不经过它。 ⚠️ 这条当天被订正过一次：最早写的是「画不出来」，那是只扫了一半的结论 —— 当时只查了「那四个 user driver 回调在全库只有一个调用方」，没查 「自动那条路会经过的类还会发哪些 delegate 回调」， 于是把「进度到不了」读成了「什么都到不了」。真正的事实是： SPUAutomaticUpdateDriver 下载时调的是 SPUCoreBasedUpdateDriver（两条路都经过它），而后者会发 delegate 的 willDownloadUpdate（即将开始下载）与 didDownloadUpdate。 ⇒ 「下载开始了」有落点，只是「下了多少」没有 —— 百分比无从得知。 分流判据是「user driver 到现在一声没吭」：弹窗那条路上 showUpdateFound 一定更早到达， 所以走到下载时状态还是「初始」的，只可能是自动那条路 —— 可派生， 不必另存一个「这次是后台检查」的位（那种位会与真实情况脱节）。
    ⇒ 那一态画出来了（B 段 3b）：不画进度条（画一条停在 0% 的进度条 比不画更让人怀疑 —— 同 B3 那条「百分比是真的，ETA 是编的」的另一面：不知道就别猜）； 那条路也不给取消入口，于是右侧不放按钮（放一个点了没反应的「取消」， 与「功能坏了」长得一模一样）。C 段第 3 行与第 7 行已按这条订正。 另一头（下载完成、等退出时装）由 delegate 的 willInstallUpdateOnQuit 送达， 已接上 —— 于是「已就绪」在自动那条路上是 可达的（在此之前它一直停在「已是最新版本」， 而更新其实已经躺在磁盘上等退出 —— 界面在说谎）。
